# Thread triage acceptance eval

Date: 2026-09-22. Source commit: `565a865`. Model: `jev-1.13.0` (the version returned by the scoring API). The baseline made no model calls.

## Dataset and method

The private dataset has 30 snapshots, split by alternating row into 15 tune and 15 test snapshots. It has 50 labeled candidate spans, of which 47 are requests for human input. Ten threads are labeled blocked and ten have nothing pending. Coverage includes clean finishes, explicit waits, answers buried under tool activity, partial answers, amended requests, withdrawn requests, optional offers, long threads, one truncated snapshot, and two historical cutoffs. A targeted audit checked 132 labels and agreed with 120 (90.9%) after applying the stated acceptance rule for `one_step_left`. This is spot check agreement, not an estimate of population label accuracy.

The baseline inspects the last text event. It reports a blocker when that event is an assistant turn containing a question mark or an imperative request marker and status is not running. Otherwise it reports nothing; its one step state is unknown. The whole window method sends a thread state containing the title, initial request, human amendments, and roughly 5,000 tokens of recent human and assistant turns to three Nouls in one API request. They judge unanswered questions, a current wait for Derick, and one remaining action before stated acceptance. The candidate method calls the shipped `score_thread`. Its evaluation pass uses request threshold zero to retain probabilities for the threshold search; this raises its measured request count and output size above a normal default call. Each scored method uses a fresh `NullCache` for every snapshot.

For the four bucket labels, blocked takes precedence, then one step left, then nothing pending, then unknown. The one step threshold stays at 0.50. The grid searches request, answered, and blocking thresholds in steps of 0.05. Its tune objective is `3 × missed blockers + stale threads + overcautious unknowns`. Ties prefer fewer missed blockers, then fewer stale threads, then proximity to 0.50. The whole window method has no separate answered probability, so that threshold has no effect there. For baseline and whole window, a reported blocker counts as stale when its thread contains any labeled answered, withdrawn, or optional request. Those methods do not identify which request caused the blocker, so this proxy can overcount. For candidate, a flagged unanswered request matching one of those labels counts. Candidate stale counts can exceed thread counts.

## Assessment and follow ups

At shipped defaults, candidate scoring ties the baseline's 7/15 test accuracy and misses five blockers against the baseline's one. It avoids six of the baseline's nine stale thread alarms on test, but its seven unknowns include four overcautious cases. Whole window at shipped defaults has 8/15 test accuracy and only one stale alarm, while missing three blockers. Its tuned setting reaches 10/15 and misses one blocker, with five stale alarms. Tune fitting improves the candidate tune objective sharply but does not generalize: test accuracy falls to 5/15 and four blockers are missed. The candidate method still saves over 98% of the estimated chief reading tokens in this calibration pass, at greater latency and cost than whole window.

The clearest candidate failure is enumeration. At t07, t08, and t20, labeled blocking requests exist but the enumerator finds zero spans, so no threshold can recover them. The enumerator relies on a trailing question mark or a request verb at the start of a sentence; embedded requests and phrasing outside that pattern can be lost. At t25, a deployment approval request is found but the default classification remains unknown. Long threads t11 and t29 account for much of the candidate input and request count because each retained span gets later dialogue windows. Whole window loses older context at its tail boundary, which can confuse whether a request was answered, while baseline mistakes completed or optional closing questions for live blockers.

Next, expand candidate enumeration using the missed event forms and add a small regression set, then rerun this fixed split with fresh outputs. Review t25's resolution and blocking scores. Keep threshold selection on tune only, and gather more labeled snapshots before changing shipped thresholds. The raw per thread outputs and private evidence remain under `evals/raw/triage/` and the ignored dataset directory.

## Rerun after enumerator fix

Source commit: `c589cdc`. One fix pass, followed by exactly one candidate-only run on all 30 unchanged snapshots with `--method candidate --force`. Each snapshot used `NullCache`; all 30 completed, with zero cache hits and no budget exhaustion. Baseline and whole window were not rerun. The original candidate outputs and eval implementation were preserved in the ignored raw directory. ### Diagnosis and changes

All missed spans inspected here were correctly tagged assistant text. None was a thinking event or an adapter role error. All snapshot statuses were idle or closed, so running-status suppression did not cause these failures and was left unchanged.

| Snapshot | Root cause before the fix |
| --- | --- |
| t07 | A reader-directed numbered list used a project prefix before an imperative outside the verb list. The earlier superseded request had the same list structure. Neither produced a candidate. |
| t08 | A reader-directed numbered list mixed a prefixed imperative, a statement about an action only the reader could take, and a pending-action statement. None ended in a question mark or began with a listed verb. |
| t20 | Both confirmation requests placed the verb after an introductory clause and colon. The current request was outside the preceding code fence, but still failed the start-of-sentence verb check. |
| t02 | The current decisions were noun phrases in a numbered list under a reader-directed heading. The only scored candidate was an earlier research question, not either labeled decision. |
| t14 | The current question was bolded, ending in `?**`, with more prose after it. The trailing-question-mark check missed it. Two earlier questions were correctly scored as answered. |
| t25 | Enumeration found the approval question. The default combination rule nevertheless required a blocking probability of at least 0.50 despite an explicit approval prerequisite in the same paragraph. |

For t02, the unrelated surviving candidate had request/answered/withdrawn/blocking probabilities `0.58 / 0.03 / 0.13 / 0.40`; request threshold 0.80 discarded it. At t14, the two earlier requests had `0.90 / 0.94 / 0.34 / 0.35` and `0.93 / 0.96 / 0.32 / 0.33`, so answer resolution correctly excluded them. The current t02 and t14 requests had no probabilities because they were never enumerated. Neither did any request at t07, t08, or t20. Thus the original four tuned test misses, t02/t08/t14/t20, were enumeration failures, not evidence that answered requests should remain blocked.

The t25 approval question had `0.87 / null / null / 0.06`; there was no later human answer or assistant withdrawal. The new combination rule treats an otherwise unanswered request in the latest assistant text as blocking when its own paragraph explicitly requires approval and no later human turn exists. Answered, withdrawn, and truncated requests still cannot use this rule to become blockers. The scorer records `approval_required`, and both the scorer and eval use the same blocking helper. This is a narrow approval-prerequisite rule, not an assumption that every closing question blocks progress. On rerun, the same question scored `0.87 / null / null / 0.05` and now blocks at defaults.

The enumerator now joins wrapped prose, separates list items and table cells, recognizes questions despite markdown formatting, checks request verbs after a colon, includes reader-addressed modal/need/approval/confirmation statements, and retains noun-phrase items under reader-directed headings. Those headings remain in candidate context. Block quotes, backtick fences, tilde fences, and thinking events remain excluded. The Noul questions and shipped thresholds were not changed. Synthetic regression tests cover the new forms, exclusions, heading scope, approval prerequisites, resolution, and scorer/eval agreement. `uv run pytest -q -m "not live"`: 176 passed, 7 deselected.

### Assessment

Enumeration now reaches the previously missing events. Tuned test misses fell from four to two and stale threads from three to one, but four overcautious unknowns appeared and bucket accuracy rose only from 5/15 to 6/15. At defaults, test misses fell from five to three and accuracy rose from 7/15 to 8/15, while stale threads increased from three to five. The rerun cost 4.75 times as much and took 4.02 times as long. Estimated chief reading tokens saved fell from 98.6% to 93.1%. This is better request coverage, not a convincing overall triage result.

The two remaining tuned test misses are t12 and t20. At t12, current retained candidates have blocking probability 0.03, below the fitted 0.15. Its old tuned blocker was an optional earlier request with request/answered/withdrawn/blocking `0.90 / 0.30 / 0.49 / 0.06`, so the earlier bucket hit was a stale alarm, not successful identification of the current dependency. At t20, the newly found current confirmation has `0.77 / null / null / 0.10`, also below 0.15. Defaults flag t20 through its older, labeled-withdrawn request (`0.72 / 0.21 / 0.13 / 0.52`); lowering the answered/withdrawn threshold to 0.10 removes that stale route and exposes the current miss. The low resolution threshold reduces stale alarms here but is not supported as a general default.

This was the requested single rerun. No further code, prompt, label, or matching changes followed its results. Because the fix used inspected test failures, this test half is a reused evaluation set, not an untouched estimate of generalization. More independent labeled snapshots are needed before adopting the fitted thresholds.
