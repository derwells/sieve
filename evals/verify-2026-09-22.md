# Citation verification acceptance eval

Date: 2026-09-22. Sieve commit before the eval: `552da76b0a9f1a9984d9343ddbb6f4eb5a2f3c2c`. The response identified the model as `jev-1.13.0` in all 40 cases. Run with `uv run python evals/verify.py run` and inspect with `uv run python evals/verify.py summary`. The runner needs `TYPESAFE_API_KEY` in its environment.

The case set has 40 hand written records. `v01` through `v20` are the fit set and `v21` through `v40` are the test set. Each has 10 true claims and 10 altered claims. Each altered half has two cases each for number, negation, scope, date, and wrong citation. Expected verdicts across all cases are 20 `supports_fully`, 12 `contradicts`, four `partially_supports`, and four `does_not_address`. Each case has one citation. The runner calls `jev_verify` once per case with a fresh `NullCache`, records every window distribution, and stores the raw response details under the ignored `evals/raw/verify/` directory. It skips completed cases on rerun.

A claim is accepted when `supports_fully >= support_threshold` and `max_contradicts < contradict_threshold`. All other claims are flagged. Grid search tested both thresholds from 0.00 through 1.00 in steps of 0.05. The objective was altered claims accepted plus true claims flagged. Ties favor fewer altered claims accepted. Remaining ties favor the pair closest to the cookbook default, then the lower thresholds. The chosen pair is **0.80 support and 0.50 contradiction**. It equals the cookbook default, so both policy rows have the same outcomes. The fit confusion is 10 true claims accepted, zero true claims flagged, zero altered claims accepted, and 10 altered claims flagged.

`unqualified_factual_relay_blocked` was true in 16/40 cases (40.0%), including 16/20 altered cases. It was false for the two partial scope or wrong citation cases in each half that had no contradiction above 0.50. All quotes matched: 35 exact and five normalised, with zero `not_found`. There was one claim and one window per case. The 40 cold calls made 40 Jev requests for 40 claim and window pairs. This run therefore cannot show any benefit from batching several pairs into one request. Usage was 29,969 input tokens and 2,322 output tokens. At the configured input token rate, total cost was $0.001258698. Summed case wall time was 37.39 seconds (19.43 fit, 17.97 test). The cost excludes any separate fetch charge.

The binary acceptance result is clean on this set, but the verdict labels miss both test scope cases. `v35` assigned 0.52 to `contradicts` and 0.45 to `partially_supports`; `v36` assigned 0.84 to `contradicts` and 0.16 to `partially_supports`. Both claims contain one supported clause and one unsupported clause. The model treated the unsupported clause as a contradiction. The fit set shows the same confusion in `v16` (0.72 contradicts, 0.28 partially supports). It also called the unrelated citation in `v19` a contradiction (0.77) rather than `does_not_address` (0.22). These are four way label errors, even though the acceptance policy flags all four. The relay block field is narrower than the acceptance policy: it can be false for a claim that the threshold policy flags, as in `v15`, `v20`, `v39`, and `v40`. Downstream callers should not treat a false relay block value as acceptance.

Follow ups: expand the set with longer pages, several citations and windows per claim, and ambiguous wording; then check whether `jev_verify` packs several pairs into one Jev request. Clarify the boundary between partial support, contradiction, and unrelated evidence in the Choice instructions and rerun on a new held out set. Consider making the relay block field reflect the same acceptance policy if callers use it as a release gate. The current 20 case test set is too small to establish a general error rate.
